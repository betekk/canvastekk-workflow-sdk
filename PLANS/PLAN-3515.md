**Branch**: feat/3515

**Base**: main

## Ticket delta vs latest base (Step 5 re-validation)

The ticket's problem statement is **partially stale against origin/main**: PR #98
(DA-3609, squash `c1851a9`, release v0.40.0, merged 2026-10-07) already landed most of
the parity work — `hard_max_runtime_seconds` (default 7200) in
`typescript/src/definition.ts`, the `effectiveRuntimeSeconds()` helper, the host
execute timeout via the effective bound (`app.ts:138`), the probe ceiling check, the
registration-payload exclusion pin, and the mirrored definition/app tests (vitest
376/376).

**What #98 missed** (the genuine remnant, and the second half of acceptance
criterion 2): python clamps its download budget to the effective bound
(`python/canvastekk_workflow_sdk/base.py:279` —
`_download_deadline(self.definition.effective_runtime_seconds)`), but TS still
derives the download deadline from the raw `timeout_seconds`
(`typescript/src/base-node.ts:259`). A TS node declaring `timeout_seconds=9000,
hard_max_runtime_seconds=7200` gets its execute() capped at 7200s while its
downloads budget from 9000s — downloads can run past the host ceiling before
execute() even starts.

## Implementation Phases

### Phase 1: download-deadline clamp + pin

- [ ] **1.1** Change the `downloadOne` deadline derivation at `typescript/src/base-node.ts:259` from `downloadDeadline(this.getDefinition().timeout_seconds)` to `downloadDeadline(effectiveRuntimeSeconds(this.getDefinition()))`, importing the helper from `./definition.js`
    — **Why:** python clamps downloads to `effective_runtime_seconds` (base.py:279); without it the TS download budget can exceed the host ceiling when `timeout_seconds > hard_max_runtime_seconds` — the parity gap #3515 files.
    — **Done when:** the call site reads `downloadDeadline(effectiveRuntimeSeconds(this.getDefinition()))` and `tsc` compiles src clean.
    — **Consumers affected:** internal (`prepareFileInputs` → `downloadOne`); `downloadDeadline`'s signature is unchanged, no other callers exist.
- [ ] **1.2** Add one test to `typescript/tests/base-node.test.ts` pinning the download budget to the effective bound: for a manifest with `timeout_seconds=9000, hard_max_runtime_seconds=7200`, the budget implied by `downloadDeadline(effectiveRuntimeSeconds(manifest))` is `7200 × 0.8` s, not `9000 × 0.8` s
    — **Why:** pins the clamp composition so a future call-site revert cannot silently re-open the ceiling; mirrors python's effective-bound depth (python pins expiry behavior, not the clamp value — the composition is where the semantics live).
    — **Done when:** the new test passes under vitest and fails if the call site reverts to raw `timeout_seconds` semantics.
    — **Consumers affected:** none.
- [ ] **1.3** Run the phase gate (light): eslint, `tsc` src+tests, vitest
    — **Why:** verification-loop contract per phase.
    — **Done when:** all three clean/green with a `tier=light` memo line in the Trace.
    — **Consumers affected:** none.
